# Алгоритм выбора имени

Один и тот же механизм «дай мне имя по случайному числу» используется в двух разных ситуациях — отличается только откуда берётся число и где выполняется код:

| Ситуация | Сид | Детерминированность | Где выполняется |
|---|---|---|---|
| Личное имя (главная страница) | дата + фингерпринт браузера | да | браузер, `public/assets/selectorMath.js` |
| Fallback для битой share-ссылки | сам токен | да | сервер, `src/names/selector.ts` |

## Примитивы

```ts
// src/utils/hash.ts
function seedToFloats(seed: string, count: number): number[]
```

Хэширует сид через SHA-256 и режет 32-байтный дайджест на непересекающиеся 8-байтные куски — на каждый нужный float по куску (значит `count` не может быть больше четырёх).

```ts
// src/names/selector.ts
function pickWeighted<T>(items: T[], weights: number[], float: number): T
function pickEqual<T>(items: T[], float: number): T
```

Обе функции чистые — ничего не знают ни про банк имён, ни про дату. `pickWeighted` выбирает категорию (учитывая `weight`), `pickEqual` — конкретное имя внутри категории (все с равной вероятностью).

## Сценарии сверху

```ts
pickFallbackName(bank, seed)           // детерминированно по сиду, только среди role: not_found
```

Сид здесь — сама строка токена. Детерминированность тут не украшение, а требование корректности: `/r/:token` и `/r/:token/og-image.png` — два независимых запроса, каждый резолвит токен заново. Пока фоллбэк брался из `crypto.randomBytes`, страница и её же OG-превью могли показать разных Святославов, а перезагрузка битой ссылки каждый раз давала новое имя. Побочный выигрыш: ответ стал чистой функцией от токена, то есть кэшируемым — см. [`03-share-link.md`](./03-share-link.md).

`pickPersonalName` (дата + фингерпринт) в серверном коде не реализована — она целиком выполняется в браузере, см. [`05-fingerprint.md`](./05-fingerprint.md) и `public/assets/selectorMath.js`. И серверная, и браузерная версии реализуют одну и ту же чистую математику дважды: полноценный общий модуль потребовал бы шага сборки фронтенда, чего проект сознательно избегает. При изменении алгоритма нужно синхронизировать обе копии вручную.

Пул кандидатов для личной ротации — всегда `bank.categories.filter(c => c.role === 'regular')`; технические категории вроде `not_found` в него не попадают (клиенту их не отдаёт и API, см. [`05-fingerprint.md`](./05-fingerprint.md)).

## Как получается float из 8 байт

```ts
function bytesToUnitFloat(bytes: Uint8Array): number {
  const uint64 = new DataView(bytes.buffer, bytes.byteOffset, 8).getBigUint64(0, false);
  const value = Number(uint64) / Number(2n ** 64n);
  return value < 1 ? value : 1 - Number.EPSILON;
}
```

Здесь есть неочевидный нюанс: `Number(uint64)` округляет до ближайшего представимого `double`, и для максимальных значений `uint64` это округление даёт ровно `2^64` — то есть само отношение может оказаться равно `1.0`, а не строго меньше единицы. Раз `pickEqual` ожидает float в `[0, 1)`, финальный клэмп на значение гарантированно меньше единицы — не защита "на всякий случай", а обязательная часть корректности при вероятности порядка 1 к 2⁶⁴. (Строго говоря, `1 - Number.EPSILON` — не ближайшее к единице число снизу, настоящее — `1 - Number.EPSILON/2`; но для инварианта `[0, 1)` достаточно любого значения строго меньше единицы.) Через эту же функцию проходит и `pickFallbackName`, и браузерное зеркало — она единственное место, где определено, что значит «float из восьми байт».

Браузерная копия (`selectorMath.js`) содержит тот же клэмп — иначе личное имя на клиенте в редких случаях могло бы вести себя иначе, чем серверная логика.
