# Деплой

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `SITE_DOMAIN` | да | — | Домен, подставляется в OG-картинки, метатеги и `/api/config.json` |
| `PORT` | нет | `3000` | Порт, который слушает Express |
| `NODE_ENV` | нет | `production` | Стандартный флаг окружения Node |
| `FINGERPRINT_SALT` | нет | значение в коде | Не секретная соль клиентского фингерпринт-хэша |
| `FINGERPRINT_FIELDS` | нет | все известные сигналы | Список сигналов через запятую — состав и порядок хэшируемых данных |

Переменной выбора локали намеренно нет — `src/i18n/locale.yaml` редактируется администратором напрямую, без выбора через окружение.

## Dockerfile

Многоступенчатая сборка: стадия `build` ставит все зависимости и компилирует TypeScript, стадия `production` копирует только скомпилированный код и production-зависимости.

Базовый образ — `node:20-slim` (Debian, glibc), не `alpine`. Причина не в том, что нативные бинарники Takumi недоступны под musl (на деле обе сборки — `@takumi-rs/core-linux-x64-gnu` и `-musl` — публикуются), а просто в том, что glibc-образ предсказуемее для отладки и меньше сюрпризов при добавлении системных зависимостей в будущем.

Банк имён и `locale.yaml` не компилируются TypeScript'ом, поэтому копируются в продакшен-стадию отдельной командой — `dist/names/bank` и `dist/i18n/locale.yaml` рядом со скомпилированным кодом, а `public/` остаётся соседом `dist/`, не вложен в него.

## docker-compose

```bash
docker network create dmz-network   # один раз, если сети ещё нет
docker compose up --build
```

Продакшен-топология подразумевает внешний nginx, уже обслуживающий другие проекты автора на том же сервере — отсюда `dmz-network: external: true` и `expose` вместо `ports`. Healthcheck бьёт в `/readyz` через `node -e ...` со встроенным модулем `http`, а не `curl`/`wget` — в `node:20-slim` их по умолчанию нет, и тащить их в образ только ради healthcheck избыточно.

Лимиты ресурсов (`mem_limit`, `cpus`) сознательно не заданы — для личного пет-проекта без значимой нагрузки это не критично; решать этот вопрос содержательно есть смысл уже на уровне Kubernetes, где лимиты реально работают.

## Graceful shutdown

```ts
process.on("SIGTERM", () => {
  healthState.isShuttingDown = true; // /readyz сразу начинает отвечать 503
  server.close(() => process.exit(0));
});
```

На практике у этого есть нюанс: `server.close()` в Node останавливает приём **новых** соединений сразу же, поэтому запрос к `/readyz`, отправленный сразу после `SIGTERM`, с большей вероятностью получит отказ в соединении, чем успеет увидеть `503` — окно для наблюдения «not ready» очень маленькое. Основная гарантия — что уже начатые запросы дорабатывают, а не обрываются, — работает и была проверена вручную. В реальном Kubernetes это не критично: там маршрутизация трафика от пода в статусе `Terminating` отключается на уровне Endpoints ещё до того, как под получает `SIGTERM`, независимо от того, что в этот момент отвечает `/readyz`.

## На будущее: Kubernetes

Фактический способ деплоя сейчас — docker-compose на собственном сервере, не Kubernetes. Но раз код уже спроектирован с раздельными liveness/readiness-пробами и конфигурацией через переменные окружения, миграция потребует только манифестов (Deployment + Service с `livenessProbe`/`readinessProbe` на `/livez`/`/readyz`), без переделки самого приложения.

Единственный нюанс при нескольких репликах: дисковый кэш `/og-image.png` локален для каждого пода (`emptyDir` не шарится) — при рестарте каждая реплика независимо перерендерит картинку один раз. Не баг: результат детерминирован по дате и совпадёт у всех реплик, просто небольшая избыточность вычислений, не имеющая значения при текущем масштабе проекта (одна реплика).
