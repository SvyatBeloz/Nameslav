# Деплой

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `SITE_DOMAIN` | да | — | Домен, подставляется в OG-картинки, метатеги и `/api/config.json` |
| `PORT` | нет | `3000` | Порт, который слушает Express; мусор или значение вне 1–65535 роняет старт с понятным сообщением, а не с `ERR_SOCKET_BAD_PORT` |
| `NODE_ENV` | нет | `production` | Стандартный флаг окружения Node; образ задаёт его сам через `ENV`, см. ниже |
| `FINGERPRINT_SALT` | нет | значение в коде | Не секретная соль клиентского фингерпринт-хэша |
| `FINGERPRINT_FIELDS` | нет | все известные сигналы | Список сигналов через запятую — состав и порядок хэшируемых данных |

Переменной выбора локали намеренно нет — `src/i18n/locale.yaml` редактируется администратором напрямую, без выбора через окружение.

## Dockerfile

Многоступенчатая сборка: стадия `build` ставит все зависимости и компилирует TypeScript, стадия `production` копирует только скомпилированный код и production-зависимости.

Сборка идёт по отдельному `tsconfig.build.json`, который исключает `**/*.test.ts` и выключает source maps. Иначе `tsc` компилировал бы и тесты (включая интеграционный, поднимающий сервер), а `COPY --from=build /app/dist` тащил бы их вместе с картами, содержащими абсолютные пути сборочной машины, прямо в продакшен-образ.

Стадия `build` явно вызывает `npm ci --include=dev`, а не просто `npm ci` — на первый взгляд избыточно (по умолчанию `npm ci` и так ставит и dev-, и обычные зависимости), но на практике npm сам переключается на `omit=dev`, если процессу виден `NODE_ENV=production` — а сборщики на базе Docker Bake (новый билдер `docker compose build`) могут прокидывать `environment:` сервиса в сборочный контекст. Без явного `--include=dev` это молча роняет `typescript` из `node_modules`, и `npm run build` падает с `tsc: not found`.

Базовый образ — `node:20-slim` (Debian, glibc), не `alpine`. Причина не в том, что нативные бинарники Takumi недоступны под musl (на деле обе сборки — `@takumi-rs/core-linux-x64-gnu` и `-musl` — публикуются), а просто в том, что glibc-образ предсказуемее для отладки и меньше сюрпризов при добавлении системных зависимостей в будущем.

Банк имён и `locale.yaml` не компилируются TypeScript'ом, поэтому копируются в продакшен-стадию отдельной командой — `dist/names/bank` и `dist/i18n/locale.yaml` рядом со скомпилированным кодом, а `public/` остаётся соседом `dist/`, не вложен в него.

Продакшен-стадия дополнительно фиксирует `ENV NODE_ENV=production`, хотя ту же переменную задаёт и `docker-compose.yml`. Это подстраховка: дефолтный обработчик ошибок Express кладёт стектрейс в тело ответа, если `NODE_ENV` не равен ровно `production`, а запустить образ можно и голым `docker run` без единой переменной. Приложение и само не зависит от этого флага (свой обработчик ошибок ничего не раскрывает в любом режиме, см. [`07-routes.md`](./07-routes.md)) — но два независимых заслона тут дешевле одного.

Продакшен-стадия завершается `USER node` перед `CMD` — процесс в контейнере не работает от root. `node:20-slim` сам создаёт этого пользователя с фиксированными UID/GID `1000:1000` (заводить своего вручную не нужно — попытка создать ещё одну группу с тем же GID `1000` просто упадёт на конфликте).

## docker-compose

```bash
docker compose up --build
```

Порт публикуется напрямую на хост (`ports`, `mode: host`) — контейнер сам торчит наружу, без внешнего reverse-proxy. Healthcheck бьёт в `/readyz` через `node -e ...` со встроенным модулем `http`, а не `curl`/`wget` — в `node:20-slim` их по умолчанию нет, и тащить их в образ только ради healthcheck избыточно.

Лимиты ресурсов (`mem_limit`, `cpus`) сознательно не заданы — для личного пет-проекта без значимой нагрузки это не критично; решать этот вопрос содержательно есть смысл уже на уровне Kubernetes, где лимиты реально работают.

### Хардening

Помимо непривилегированного пользователя (см. выше), контейнер запускается с:

- `read_only: true` — корневая файловая система только для чтения. Приложение в рантайме не пишет никуда: статическая OG-карточка мемоизирована в памяти, дискового кэша больше нет (см. [`06-og-rendering.md`](./06-og-rendering.md)).
- `tmpfs: - /tmp` — страховка на случай, если что-то в рантайме (Node, нативный аддон Takumi) захочет писать во временную директорию; сам код приложения туда не пишет, но /tmp read-only с большой вероятностью что-нибудь да сломает молча.
- `cap_drop: - ALL` — обычному Node-процессу на непривилегированном порту не нужны никакие Linux capabilities.
- `security_opt: [no-new-privileges=true]` — процесс не может повысить привилегии даже через setuid-бинарники.

Раньше сервису нужна была писабельная `./cache` для дневной OG-картинки; теперь кэша на диске нет, поэтому никаких предварительных `mkdir`/`chown` на хосте не требуется.

### Банк имён и локаль без пересборки

`docker-compose.yml` дополнительно монтирует банк имён и `locale.yaml` как read-only volume поверх того, что скопировано в образ на билде:

```yaml
volumes:
  - ./src/names/bank:/app/dist/names/bank:ro
  - ./src/i18n/locale.yaml:/app/dist/i18n/locale.yaml:ro
```

И то, и другое читается сервером только один раз при старте (см. [`01-name-bank.md`](./01-name-bank.md), [`04-i18n.md`](./04-i18n.md)), поэтому изменение файлов на хосте требует `docker compose restart`, а не пересборки образа — удобно при правке текстов интерфейса или добавлении новых категорий имён без полного цикла `docker compose up --build`.

## Graceful shutdown

```ts
const shutdown = () => {
  healthState.isShuttingDown = true; // /readyz сразу начинает отвечать 503
  server.close(() => process.exit(0));
  server.closeIdleConnections(); // не держать процесс на idle keep-alive соединениях
  setTimeout(() => process.exit(0), SHUTDOWN_GRACE_MS).unref(); // принудительный выход, если запрос завис
};
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);
```

`server.close()` сам по себе ждёт **все** открытые соединения, включая idle keep-alive, — без `closeIdleConnections()` процесс висел бы до SIGKILL оркестратора. Fallback-таймер страхует от зависшего in-flight запроса. На практике есть нюанс: `server.close()` останавливает приём **новых** соединений сразу же, поэтому запрос к `/readyz`, отправленный сразу после `SIGTERM`, с большей вероятностью получит отказ в соединении, чем успеет увидеть `503` — окно для наблюдения «not ready» очень маленькое. Основная гарантия — что уже начатые запросы дорабатывают, а не обрываются. В реальном Kubernetes это не критично: там маршрутизация трафика от пода в статусе `Terminating` отключается на уровне Endpoints ещё до того, как под получает `SIGTERM`, независимо от того, что в этот момент отвечает `/readyz`.

## На будущее: Kubernetes

Фактический способ деплоя сейчас — docker-compose на собственном сервере, не Kubernetes. Но раз код уже спроектирован с раздельными liveness/readiness-пробами и конфигурацией через переменные окружения, миграция потребует только манифестов (Deployment + Service с `livenessProbe`/`readinessProbe` на `/livez`/`/readyz`), без переделки самого приложения.

Единственный нюанс при нескольких репликах: статическая OG-карточка мемоизирована в памяти каждого процесса — при рестарте каждая реплика независимо перерендерит её один раз. Не баг: картинка одинакова для всех и не зависит от даты, так что это небольшая избыточность вычислений, не имеющая значения при текущем масштабе проекта (одна реплика).
